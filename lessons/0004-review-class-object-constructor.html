복습: class, object, constructor

레슨 0004 · 복습 세션 (큐 진행 아님, 0003 재확인) · Money와 다른 도메인으로 처음부터 다시

0003에서 Money를 만들며 네 가지 지점에서 막혔었다: this, field 초기화 누락 시 기본값, object 생성 시점, constructor invariant(fail fast). 전체적으로 애매하다고 했으니, 오늘은 새로 안 배우고 같은 개념을 다른 도메인에서 기억으로 다시 꺼내는 연습만 한다. 막히면 0003 레슨이나 cheatsheet를 봐도 되지만, 먼저 기억에서 꺼내보는 게 핵심이다.

4가지 재확인 포인트 — 빠른 recall

코드를 보기 전에 먼저 스스로 답해보자 (답은 접혀있지 않으니 바로 아래 읽지 말고 생각부터).

Q1. constructor의 parameter 이름과 field 이름이 같을 때, field 쪽을 가리키기 위해 앞에 붙이는 키워드는?

Q2. constructor에서 int field에 값을 대입하는 줄을 깜빡하면, 그 field는 무슨 값으로 남는가? (숫자로 답)

Q3. object가 실제로 만들어지는(constructor가 실행되는) 시점은 코드에서 어떤 키워드가 있는 줄이 실행될 때인가?

Q4. constructor에서 잘못된 값이면 바로 예외를 던져서, 애초에 잘못된 상태의 object가 존재하지 못하게 막는 이 패턴을 영어로 뭐라 부르는가? (두 단어)

Hands-on: PageRequest — 처음부터 다시 작성

실무 백엔드에서 목록 API를 만들 때 거의 항상 등장하는 패턴이다 — 페이지네이션 요청. Money 때와 똑같은 원칙들이 그대로 적용된다. 이번엔 시작 코드 없이, 레슨 0003에서 겪었던 네 가지 실수를 스스로 피해가며 처음부터 작성해보자.

practice/0004-review-class-object-constructor/PageRequest.java에 아래 조건으로 작성:

  • field: page (int, 0부터 시작하는 페이지 번호), size (int, 한 페이지당 항목 수)
  • constructor: page와 size를 받는다.
    • page가 음수면 IllegalArgumentException
    • size가 1보다 작거나 100보다 크면 IllegalArgumentException (한 번에 100개 초과 조회를 막는 실무 관례)
  • method nextPage(): 원본은 그대로 두고, page가 1 증가한 새로운 PageRequest object를 반환 (size는 동일하게 유지)
  • main에서 각각 따로 실행해서 확인 (0003 때처럼 한 번에 다 넣으면 첫 예외에서 멈춘다는 것 기억할 것):
    • 정상 생성 → nextPage() 호출 → 원본과 새 object의 page 값이 다른지 확인 (원본이 안 바뀌었는지가 핵심)
    • page를 음수로 생성 → 예외가 어느 줄에서 나는지 확인 (constructor인지 다른 곳인지)
    • size를 101로 생성 → 예외 확인
스스로 체크리스트 (다 쓰고 나서 코드를 다시 읽으며 확인):
  • constructor 안에서 this.page와 this.size 둘 다 대입했는가? (하나 빠뜨리기 쉬움 — 0003에서 실제로 겪은 실수)
  • nextPage()가 this.page를 직접 바꾸고 있진 않은가? (+=를 썼다면 의심할 것)
  • 예외를 일으키는 new PageRequest(...) 줄이, print문과 무관하게 그 줄 자체에서 실행된다는 걸 이해하고 테스트를 구성했는가?
막히면 바로 물어보되, 이번엔 먼저 0003의 Money 코드와 비교해서 "여기가 그거랑 똑같은 패턴이네" 하고 스스로 연결지어본 다음에 물어보자 — 그게 이 복습의 목적이다.
