class, object, constructor

레슨 0003 · 문법 기초 큐 3/11 · invoice-app의 Invoice, LineItem이 바로 class다

지금까지는 int, String 같은 이미 만들어진 type만 썼다. 이제부터는 직접 type을 만드는 법을 배운다. invoice-app의 Invoice, LineItem, Customer가 전부 class다 — 이 레슨이 그 설계의 기초다.

1. class는 설계도, object는 실체

class는 데이터(field)와 동작(method)을 묶어놓은 설계도다. object는 그 설계도로 new 키워드를 통해 만들어낸 실체 — 메모리에 실제로 존재하는 것이다. 

public class Invoice {
    // field — object의 상태
    String status;
    int amountInCents;
}

Invoice inv = new Invoice(); // object 생성

같은 class로 new를 여러 번 호출하면, 각각 독립된 상태를 가진 object가 여러 개 생긴다.

출처: Oracle Java Tutorials — Classes

2. constructor — object가 생성될 때 실행되는 것

constructor는 class와 이름이 같고, 반환 타입이 없는 특별한 메서드다. new가 호출되는 순간 자동으로 실행되며, field를 초기값으로 채우는 역할을 한다. 

public class Invoice {
    String status;
    int amountInCents;

    public Invoice(String status, int amountInCents) {
        this.status = status;
        this.amountInCents = amountInCents;
    }
}

Invoice inv = new Invoice("DRAFT", 15000);

3. this — field와 parameter 이름이 겹칠 때

위 코드에서 parameter 이름을 field 이름과 똑같이 지었다. 이러면 그냥 status = status;라고 쓰면 parameter가 자기 자신에게 대입되어 field는 그대로 비어있게 된다. this.status는 "이 object의 field"라는 뜻으로, 둘을 구분해준다.

기억할 것: this.필드명 = object의 field, 필드명 = 그냥 가장 가까운 local parameter. 이름이 겹칠 때만 this가 꼭 필요하다.

4. default constructor

constructor를 하나도 안 만들면, 컴파일러가 자동으로 인자 없는 constructor(default constructor)를 넣어준다. 그런데 constructor를 하나라도 직접 만들면 default constructor는 더 이상 자동으로 생기지 않는다 — 인자 없는 버전이 필요하면 직접 추가해야 한다. 

public class Invoice {
    public Invoice(String status, int amountInCents) { ... }
    // 여기서 new Invoice()는 컴파일 에러 — 위 constructor가 있어서 default가 사라짐
}

출처: Oracle Java Tutorials — Creating Objects

Quarkus/CDI에서 @ApplicationScoped bean을 프록시로 감쌀 때, CDI는 인자 없는 constructor가 있어야 프록시를 만들 수 있다. @Inject constructor 하나만 만들고 no-arg constructor를 깜빡하면 CDI가 배포 시점에 에러를 던졌던 경험 — 그게 바로 이 규칙이 프레임워크 레벨에서 드러난 것이다.

5. invoice-app에 바로 적용

Invoice class를 만들 때, constructor에서 status와 amountInCents를 필수로 받게 하면 "상태 없는 invoice", "금액 없는 invoice" 같은 불완전한 object가 애초에 생성되지 못하게 막을 수 있다. 이건 나중에 배울 validation의 가장 원초적인 형태다.
