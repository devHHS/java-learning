exception handling — checked vs unchecked

레슨 0013 · 문법 기초 큐 10/11 · try/catch, throw/throws, 그리고 컴파일러가 강제하는 것과 안 하는 것

invoice-app에서 존재하지 않는 receipt id를 조회하면 무슨 일이 일어나야 할까? null을 반환하고 넘어가면, 그 null을 쓰는 코드 어딘가에서 언젠가 NullPointerException이 터진다 — 그것도 원인과 먼 곳에서. 오늘은 "문제가 생겼다"는 걸 명시적으로 알리는 방법(exception)과, Java가 그중 일부를 컴파일 타임에 강제로 처리시키는 이유를 배운다.

1. 문제 상황 — 처리 안 된 예외

int[] numbers = {1, 2, 3};
System.out.println(numbers[5]);   // index 5는 없다

실행하면:

Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException:
    Index 5 out of bounds for length 3
    at Runner.main(Runner.java:3)

예외가 발생한 지점에서 아무도 잡지 않으면, 그 예외는 호출한 곳으로, 또 그걸 호출한 곳으로 계속 전파(propagate)되다가 결국 main까지 도달해서 프로그램이 그 자리에서 죽는다. 이 stack trace 자체가 "어디서 뭐가 잘못됐는지"를 알려주는 정보다 — 지우지 말고 읽는 습관이 먼저다.

2. try / catch / finally

try {
    System.out.println(numbers[5]);
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("index 범위 초과: " + e.getMessage());
} finally {
    System.out.println("이 줄은 예외 발생 여부와 상관없이 항상 실행된다");
}

try block 안에서 예외가 발생하면, 그 즉시 try block의 나머지는 건너뛰고 맞는 catch block으로 점프한다. finally는 예외가 나든 안 나든, catch에서 처리되든 안 되든 항상 실행된다 (자원 정리 등에 쓰인다).

3. checked vs unchecked — 오늘의 핵심

모든 예외는 Throwable의 하위 클래스다. 그중 RuntimeException(그리고 그 하위)과 Error(그리고 그 하위)를 뺀 나머지를 checked exception이라 부른다.

"Checked exceptions are subject to the Catch or Specify Requirement. All exceptions are checked exceptions, except for those indicated by Error, RuntimeException, and their subclasses." — Oracle Java Tutorials — The catch or Specify Requirement

"Catch or Specify"란: checked exception이 발생할 수 있는 코드는 반드시 ① try로 잡거나, ② method 시그니처에 throws로 명시해야 한다 — 안 하면 컴파일이 안 된다. RuntimeException(unchecked)은 이 요구사항에서 제외된다 — 컴파일러가 강제하지 않는다.

왜 이렇게 나눴을까?

"If a client can reasonably be expected to recover from an exception, make it a checked exception. If a client cannot do anything to recover from the exception, make it an unchecked exception." — Oracle Java Tutorials — Unchecked Exceptions: The Controversy

예: 파일을 여는 코드는 그 파일이 없을 수도 있다는 걸 충분히 예상 가능하고, 호출한 쪽이 "다른 경로 시도" 같은 복구를 할 수 있다 — 그래서 IOException은 checked. 반면 null에 method를 호출한 것(NullPointerException)은 프로그래밍 실수지, 호출한 쪽이 복구할 방법이 없다 — 그래서 unchecked.

4. throw로 던지기, throws로 선언하기, custom exception 만들기

// unchecked — RuntimeException을 상속
public class EmployeeNotFoundException extends RuntimeException {
    public EmployeeNotFoundException(String message) {
        super(message);
    }
}

public Employee findByIdOrThrow(Long id) {
    if (!store.containsKey(id)) {
        throw new EmployeeNotFoundException("id=" + id);   // throw — 실제로 던짐
    }
    return store.get(id);
}   // throws 선언 없음 — unchecked라 컴파일러가 요구 안 함

"All methods use the throw statement to throw an exception. The throw statement requires a single argument: a throwable object." — Oracle Java Tutorials — How to Throw Exceptions

checked exception을 만들 땐 Exception을 상속한다. 이 경우 method 시그니처에 throws가 필수다: 

// checked — Exception을 상속
public class InvalidEmployeeDataException extends Exception {
    public InvalidEmployeeDataException(String message) {
        super(message);
    }
}

public void validateDepartment(String department) throws InvalidEmployeeDataException {
    if (department == null || department.isBlank()) {
        throw new InvalidEmployeeDataException("department is required");
    }
}

throw(동사, 단수)는 실제로 던지는 statement, throws(method 시그니처에 붙는 키워드)는 "이 method가 checked exception을 던질 수 있다"는 선언이다. 둘은 다른 자리에, 다른 목적으로 쓰인다.

Spring에서는 @ExceptionHandler(EmployeeNotFoundException.class)를 붙인 method가 controller/service에서 던진 exception을 잡아 HTTP 응답(예: 404)으로 바꿔준다. Quarkus에서는 @ServerExceptionMapper가 똑같은 역할을 한다 — exception을 RestResponse로 매핑. 오늘 만든 custom exception이 나중에 이 자리에 그대로 들어간다.

5. invoice-app에 바로 적용

receipt를 id로 조회하는 repository method가 못 찾았을 때 null을 반환하는 대신 ReceiptNotFoundException(unchecked) 같은 custom exception을 던지면, 나중에 Spring이 그 exception 하나로 "404 Not Found" 응답까지 자동으로 이어줄 수 있다.

"@Controller and @ControllerAdvice classes can have @ExceptionHandler methods to handle exceptions from controller methods." — Spring Framework Reference — @ExceptionHandler

Hands-on: EmployeeService — checked와 unchecked를 나란히

practice/0013-exception-handling/p0013/에 시작 코드 없이 전부 직접 작성한다. 0012의 Employee/repository와 비슷한 모양이지만, 오늘은 "못 찾으면 null" 대신 "못 찾으면 예외"로 바꿔본다.

1) Employee.java — field: id(Long), name(String), department(String). constructor, getter 세 개. (새로 배울 것 없음.)

2) EmployeeNotFoundException.java — RuntimeException을 상속(unchecked). String message를 받는 constructor 하나, super(message) 호출.

3) InvalidEmployeeDataException.java — Exception을 상속(checked). 마찬가지로 String message constructor, super(message).

4) EmployeeService.java — field: Map<Long, Employee> store (constructor에서 new HashMap<>()로 초기화). method 세 개:

  • Employee save(Employee e) — e.getId()를 key로 저장하고 e 반환.
  • Employee findByIdOrThrow(Long id) — 있으면 반환, 없으면 EmployeeNotFoundException을 throw. (unchecked라 시그니처에 throws 필요 없음.)
  • void validateDepartment(String department) throws InvalidEmployeeDataException — department가 null이거나 blank면 InvalidEmployeeDataException을 throw.

5) Runner.java — 순서대로, 각 단계 결과를 직접 눈으로 확인하면서 진행:

  1. EmployeeService 생성, Employee 하나 저장.
  2. 존재하는 id로 findByIdOrThrow 호출 → 이름 출력. (try/catch 없이도 컴파일된다 — 왜 그런지 이미 알고 있을 것.)
  3. 존재하지 않는 id로 findByIdOrThrow를 try/catch 없이 한 번 호출해보고 실행 — stack trace를 직접 읽어본다. 그다음 try/catch로 감싸서 catch block에서 e.getMessage()를 출력하도록 고친다.
  4. validateDepartment(null)을 try/catch 없이 그냥 호출하는 코드를 써본다 — 컴파일 에러가 날 것이다. 에러 메시지를 읽고, try/catch로 감싸서 catch block에서 메시지를 출력하도록 고친다.
스스로 체크리스트:
  • EmployeeNotFoundException은 RuntimeException을, InvalidEmployeeDataException은 Exception을 상속했는가? (이 한 글자 차이가 checked/unchecked를 가른다.)
  • findByIdOrThrow엔 throws가 없고, validateDepartment엔 throws가 있는 이유를 설명할 수 있는가?
  • 3번과 4번에서 각각 무슨 에러(런타임 예외 vs 컴파일 에러)를 봤는지, 왜 다른지 구분할 수 있는가?
