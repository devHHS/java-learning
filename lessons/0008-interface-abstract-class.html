interface와 abstract class — 언제 뭘 쓰는가

레슨 0008 · 문법 기초 큐 7/11 · 0007에서 미뤘던 질문

0007에서 PaymentMethod를 예로 들면서 "카드/계좌이체/PayPal이 extends해서 process()를 override"한다고 했다. 근데 그게 꼭 class여야 할까? 결제 수단들이 공유하는 코드가 거의 없다면, 물려줄 게 없으니 extends 대신 다른 게 필요하다 — 그게 interface다.

1. interface — "계약(contract)"

interface는 무엇을 할 수 있는지만 정의하고, 어떻게 하는지는 정의하지 않는다. Oracle 문서의 정의가 정확하다:

"There are a number of situations in software engineering when it is important for disparate groups of programmers to agree to a 'contract' that spells out how their software interacts... Generally speaking, interfaces are such contracts." — Oracle Java Tutorials — Interfaces 

public interface DiscountPolicy {
    double apply(double amount);   // 몸통 없음, signature만
}

public class PercentageDiscount implements DiscountPolicy {
    private double percent;
    public PercentageDiscount(double percent) { this.percent = percent; }

    @Override
    public double apply(double amount) {
        return amount - (amount * percent / 100);
    }
}

extends 대신 implements를 쓴다. interface 자체는 instantiate 불가 — new DiscountPolicy()는 안 되고, 구현한 class를 통해서만 쓸 수 있다.

2. abstract class — "일부만 완성된 부모"

abstract class는 0007의 부모 class와 거의 같은데, 한 가지가 다르다: method를 몸통 없이 선언만 하고 subclass에게 구현을 강제할 수 있다.

"An abstract class is a class that is declared abstract—it may or may not include abstract methods. Abstract classes cannot be instantiated, but they can be subclassed." — Oracle Java Tutorials — Abstract Methods and Classes 

public abstract class PaymentMethod {
    protected String accountId;
    public PaymentMethod(String accountId) { this.accountId = accountId; }

    public boolean validate() {                 // 몸통 있음 — 그대로 상속
        return accountId != null && !accountId.isBlank();
    }

    public abstract void process(double amount); // 몸통 없음 — subclass가 반드시 구현
}

PaymentMethod 자체는 new PaymentMethod("x")로 못 만든다 (interface와 동일). 하지만 validate()처럼 공통 코드를 실제로 들고 있을 수 있다는 게 interface와의 결정적 차이다.

3. 핵심 차이

interfaceabstract class
field사실상 상수만 (public static final)일반 instance field 가능
method 구현기본적으로 없음 (signature만)구현 있는 것 + 없는 것 섞임
constructor없음있음 (subclass가 super()로 호출)
한 class가 가질 수 있는 수implements 여러 개extends 딱 하나

"...with abstract classes, you can declare fields that are not static and final... With interfaces, all fields are automatically public, static, and final... In addition, you can extend only one class... whereas you can implement any number of interfaces." — Oracle Java Tutorials — Abstract Methods and Classes

4. 언제 뭘 쓰는가 — Oracle 가이드라인

abstract class를 고려할 때:

  • 서로 밀접하게 관련된 class끼리 코드를 공유하고 싶을 때 (validate() 같은 것)
  • subclass들이 공통 field나 method를 많이 가질 것으로 예상될 때
  • public이 아닌 접근 수준(protected 등)이 필요할 때

interface를 고려할 때:

  • 서로 관련 없는 class들이 구현할 것으로 예상될 때
  • "누가 구현하는지는 신경 안 쓰고, 무엇을 할 수 있는지만" 규정하고 싶을 때
  • 한 class가 여러 계약을 동시에 만족해야 할 때 (다중 implements)

원문: Oracle Java Tutorials — Abstract Methods and Classes

PaymentMethod(카드/계좌이체/PayPal)는 validate() 같은 공통 코드를 공유할 여지가 있으니 abstract class가 자연스럽다. 반면 DiscountPolicy(정률 할인/정액 할인/쿠폰)는 서로 코드를 공유할 게 거의 없고 "amount를 받아서 amount를 반환한다"는 계약만 중요하니 interface가 맞다. Spring Data JPA의 JpaRepository도 interface다 — Spring이 런타임에 구현체를 대신 만들어주는 게 가능한 이유가, interface는 "무엇을 하는지"만 규정하고 "어떻게"는 개발자가 신경 쓰지 않아도 되기 때문이다.

5. invoice-app에 바로 적용

영수증을 CSV로도, PDF로도 내보내야 한다면 ReceiptExporter interface에 export(receipt) signature만 정의하고, CsvExporter/PdfExporter가 각자 implements한다. 두 구현이 공유할 코드가 거의 없으니 abstract class보다 interface가 맞는 선택이다.
