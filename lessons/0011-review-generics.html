0010 끝에 "오늘 한 것에 대해 이해를 제대로 못 했다"고 스스로 평가했다. hands-on(PagedResult, firstOrNull)은 다 해냈지만 개념이 아직 단단하지 않다는 뜻이다. 오늘은 새로 안 배우고, 같은 개념을 다른 모양으로 기억에서 다시 꺼내는 연습만 한다. REST API가 응답을 감싸서 내려주는 { success, data, error } 형태의 envelope는 백엔드에서 아주 흔한 패턴이고, invoice-app의 controller도 결국 이런 형태를 반환하게 될 것이다.

Hands-on: ApiResponse<T> — 처음부터 다시 작성

0010에서는 PagedResult<T>(생성자로 바로 만드는 방식)와 PageUtils.firstOrNull(별도 클래스의 generic method)을 썼다. 이번엔 하나의 클래스 안에서 generic method 두 개가 그 클래스 자신의 generic type을 반환하는, 조금 더 나아간 모양을 연습한다. 이것도 시작 코드 없이 처음부터 작성한다.

1) practice/0011-review-generics/p0011/Product.java — 감쌀 대상이 될 간단한 클래스. field: id(Long), name(String), price(double). constructor 하나(세 값 다 받음), getter 세 개. (0003~0006에서 이미 여러 번 만든 수준 — 여기선 새로 배울 것 없음.)

2) practice/0011-review-generics/p0011/ApiResponse.java — 오늘의 핵심. 아래 조건으로 작성:

  • class 자체가 <T>를 갖는 generic class다.
  • field: success(boolean), data(T), errorMessage(String)
  • constructor: 세 field를 모두 받아서 대입한다. (이 constructor를 Runner에서 직접 부르진 않을 것이다 — 아래 static method 두 개를 통해서만 쓴다.)
  • static factory method 두 개, 각각 자기 자신의 <T>를 선언한다 (class의 T와는 별개로 method 앞에 붙이는 것 — 0010의 firstOrNull과 똑같은 위치):
    • public static <T> ApiResponse<T> success(T data) — success=true, 받은 data, errorMessage=null로 새 ApiResponse<T>를 만들어 반환
    • public static <T> ApiResponse<T> error(String message) — success=false, data=null, 받은 message로 새 ApiResponse<T>를 만들어 반환
  • getter 세 개: isSuccess(), getData(), getErrorMessage()

3) practice/0011-review-generics/p0011/Runner.java — 완성본 없이 직접 작성:

  • Product 하나 생성 (예: id=1L, name="Keyboard", price=49.99)
  • ApiResponse.success(...)로 그 Product를 감싸서 ApiResponse<Product> 하나 생성 → isSuccess()와 getData().getName() 출력
  • ApiResponse.error("Product not found")로 실패 케이스 하나 생성 → isSuccess(), getErrorMessage() 출력, getData()가 null인지도 확인
스스로 체크리스트 (다 쓰고 나서 코드를 다시 읽으며 확인):
  • class ApiResponse<T>처럼 클래스 선언 자체에 <T>를 붙였는가?
  • success/error method 앞에 각각 <T>를 따로 선언했는가? (class의 <T>와 이름은 같아도 별개의 선언이다)
  • data field의 타입이 Object가 아니라 T인가?
  • Runner에서 ApiResponse<Product>처럼 타입을 쓸 때, 그게 type parameter가 아니라 type argument라는 걸 구분할 수 있는가?
막히면 바로 물어보되, 먼저 0010의 firstOrNull 코드와 비교해서 "여기 <T> 위치가 그거랑 똑같네" 하고 스스로 연결지어본 다음에 물어보자. bounded type(<T extends Number>)이나 wildcard는 오늘도 범위 밖이지만 궁금하면 짧게 설명해줄 수 있다.
