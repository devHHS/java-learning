inheritance와 polymorphism

레슨 0007 · 문법 기초 큐 6/11 · 이미 던지고 있던 예외에서 시작한다

Money.java constructor에서 throw new IllegalArgumentException();을 썼었다. 사실 IllegalArgumentException은 RuntimeException을 상속받은 class고, RuntimeException은 Exception을, Exception은 Throwable을 상속받는다. 지금까지 이름도 몰랐던 inheritance를 이미 매번 쓰고 있었던 것이다.

1. extends — 부모의 것을 물려받는다

extends 키워드로 한 class가 다른 class의 member를 물려받게 만든다. Java는 단일 상속이다 — Object를 빼면 모든 class는 딱 하나의 direct superclass만 가진다. 

public class Notification {
    protected String recipient;
    public Notification(String recipient) { this.recipient = recipient; }
    public void send() { System.out.println("일반 알림을 " + recipient + "에게 보냄"); }
}

public class EmailNotification extends Notification {
    private String subject;
    // ...
}

무엇이 물려지는가: public/protected member는 그대로 상속된다. private member는 상속되지 않는다 — 부모가 public/protected getter를 열어뒀다면 그걸 통해서만 접근 가능하다. constructor는 상속되지 않는다 — 대신 subclass의 constructor에서 super(...)로 부모 constructor를 직접 불러야 한다.

출처: Oracle Java Tutorials — Overriding and Hiding Methods

2. protected가 여기서 쓰인다 (0005에서 미뤘던 것)

0005에서 "protected는 inheritance에서 다시 다룬다"고 했던 게 이거다. Notification의 recipient를 private로 막으면 EmailNotification이 아예 접근을 못 한다. public으로 열면 아무 class나 다 건드릴 수 있다. protected는 그 중간 — "subclass는 접근 가능, 그 외 남은 다 막힘"이다.

3. super — 부모 constructor 호출

public class EmailNotification extends Notification {
    private String subject;

    public EmailNotification(String recipient, String subject) {
        super(recipient);       // 부모의 constructor에게 recipient 처리를 넘김
        this.subject = subject;
    }
}

super(recipient)는 반드시 constructor의 첫 줄에 와야 한다 — 부모가 먼저 자기 상태를 갖추고 나서, 자식이 자기 것을 추가하는 순서다.

4. overriding — 같은 signature, 다른 동작

부모에 있는 instance method와 이름 + 매개변수가 완전히 같은 method를 subclass에서 다시 정의하는 것을 override라고 부른다. 

public class EmailNotification extends Notification {
    @Override
    public void send() {
        System.out.println("이메일 " + subject + "를 " + recipient + "에게 보냄");
    }
}

@Override는 필수는 아니지만, "이건 부모 걸 재정의한 거다"를 컴파일러가 확인해주므로 항상 붙인다 — signature를 잘못 적으면(오타 등) 컴파일 에러로 바로 잡아준다.

5. polymorphism — 선언 타입이 아니라 실제 타입이 이긴다

List<Notification>에 Notification, EmailNotification, SmsNotification을 섞어 담고 send()를 부르면, 변수의 선언 타입(Notification)이 아니라 각 object가 실제로 무엇으로 만들어졌는지에 따라 다른 send()가 실행된다.

Oracle 원문: "The Java virtual machine (JVM) calls the appropriate method for the object that is referred to in each variable. It does not call the method that is defined by the variable's type." — Oracle Java Tutorials — Polymorphism

이게 왜 유용한가: for (Notification n : queue) { n.send(); } 한 줄로 모든 종류의 알림을 다 처리할 수 있다. if (n instanceof EmailNotification) ... else if ... 같은 분기를 안 짜도 된다 — polymorphism이 그 분기를 대신 해준다.

Money.java의 throw new IllegalArgumentException()을 나중에 catch (RuntimeException e)로 잡을 수 있는 것도 같은 원리다 — IllegalArgumentException은 RuntimeException이기도 하니까(is-a 관계). exception handling 큐 항목에서 이걸 제대로 다룬다. Spring Boot의 @ControllerAdvice도 이 상속 계층을 이용해서 "이 계열의 예외는 다 여기서 잡는다"는 걸 구현한다.

6. invoice-app에 바로 적용

결제 수단이 여러 개(카드, 계좌이체, PayPal)라면 PaymentMethod 부모 class를 만들고 각 결제 방식이 extends해서 자기만의 process()를 override하게 만들 수 있다. List<PaymentMethod>로 관리하면 결제 로직을 추가할 때마다 기존 코드를 안 건드리고 새 subclass만 추가하면 된다 — 이 확장성이 inheritance/polymorphism을 쓰는 실질적 이유다.
