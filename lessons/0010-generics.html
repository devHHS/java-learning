generics — 타입을 매개변수로 받기

레슨 0010 · 문법 기초 큐 9/11 · 0009에서 미뤄둔 <> 문법, 이제 제대로

Spring Data JPA의 repository는 이렇게 생겼다: interface ReceiptRepository extends JpaRepository<Receipt, Long>. <Receipt, Long> 부분이 정확히 뭘 하는 건지 지금은 설명 못 할 것이다. 오늘 배우면 설명할 수 있게 된다.

1. 문제 상황 — generics가 없다면

0009에서 List<String>을 그냥 썼지만, <String>을 빼고 옛날 방식(Java 5 이전)으로 쓴다면 이렇게 된다. 

List box = new ArrayList();   // 타입 지정 없음 — 뭐든 담을 수 있음
box.add(42);
box.add("문자열");             // 컴파일러가 막지 못함

Integer x = (Integer) box.get(1);   // 런타임에 캐스팅 실패 — ClassCastException

"There is no way to verify, at compile time, how the class is used. One part of the code may place an Integer in the box and expect to get Integers out of it, while another part of the code may mistakenly pass in a String, resulting in a runtime error." — Oracle Java Tutorials — Generic Types

문제의 핵심: 타입 오류가 컴파일 타임이 아니라 런타임에 터진다. 배포하고 나서야 알게 된다는 뜻이다.

2. 해결 — type parameter

List<String> box = new ArrayList<>();
box.add("문자열");
box.add(42);        // 컴파일 에러 — 여기서 바로 막힘

String s = box.get(0);   // 캐스팅 필요 없음, 컴파일러가 이미 String인 걸 앎

<String>은 "이 List가 다룰 타입은 String이다"를 컴파일러에게 알려주는 것이다. 0009에서 List<String>, Map<Integer, Product>를 쓸 때 이미 사용한 문법이다 — 그때는 "이런 게 있다"까지만, 오늘은 "왜, 어떻게"를 본다.

3. 직접 정의하기 — generic class

List, Map은 이미 만들어진 generic class다. 이제 직접 만들어본다. 백엔드에서 흔한 패턴: 목록 조회 API가 "항목들 + 전체 개수"를 함께 반환하는 PagedResult. 

public class PagedResult<T> {
    private List<T> items;
    private int totalCount;

    public PagedResult(List<T> items, int totalCount) {
        this.items = items;
        this.totalCount = totalCount;
    }

    public List<T> getItems() { return items; }
    public int getTotalCount() { return totalCount; }
}

PagedResult<Receipt> page = new PagedResult<>(receipts, 42);

"A generic type is a generic class or interface that is parameterized over types... A type variable can be any non-primitive type you specify." — Oracle Java Tutorials — Generic Types

T는 클래스 이름 옆 <T>에서 선언되는 type parameter다 — "실제 타입은 나중에 정해진다"는 placeholder. new PagedResult<Receipt>(...)처럼 실제로 쓸 때 Receipt가 그 자리를 채운다 (이걸 type argument라 부른다). 관례상 type parameter는 대문자 한 글자 — T(Type), E(Element), K/V(Key/Value) — 를 쓴다.

4. generic method — method 하나만 generic으로

클래스 전체가 아니라 method 하나만 타입을 매개변수로 받을 수도 있다. 

public static <T> T firstOrNull(PagedResult<T> result) {
    if (result.getItems().isEmpty()) return null;
    return result.getItems().get(0);
}

"The syntax for a generic method includes a list of type parameters, inside angle brackets, which appears before the method's return type." — Oracle Java Tutorials — Generic Methods

static <T> T firstOrNull(...)에서 앞의 <T>는 "이 method는 T라는 타입을 하나 받는다"는 선언이고, 뒤의 T는 return type이다. 순서가 중요하다 — <T>가 먼저, return type이 그다음.

Quarkus Panache의 repository도 똑같은 패턴이다: public class PersonRepository implements PanacheRepository<Person>. <Person>이 "이 repository가 관리하는 entity가 Person"이라는 뜻이다. Spring Data JPA의 JpaRepository<T, ID>도 정확히 같은 개념이고, type parameter가 하나 더 있을 뿐이다 (관리할 entity 타입 + 그 entity의 id 타입).

5. invoice-app에 바로 적용

interface ReceiptRepository extends JpaRepository<Receipt, Long>에서 T 자리엔 Receipt(이 repository가 관리하는 entity), ID 자리엔 Long(Receipt의 primary key 타입)이 들어간다.

"The central interface in the Spring Data repository abstraction is Repository. It takes the domain class to manage as well as the identifier type of the domain class as type arguments." — Spring Data JPA Reference — Core Concepts

이 한 줄을 쓰는 순간 findById(Long id)가 Optional<Receipt>를 반환한다는 것까지 컴파일러가 안다 — 캐스팅도, 런타임 타입 오류도 없다. 이게 generics 없이는 불가능한 API 설계다.
