복습: generics — repository 패턴 (두 개의 type parameter)

레슨 0012 · 복습 세션 (큐 진행 아님, 0010/0011 재확인) · 큐는 9/11 유지

0011에서 ApiResponse<T>는 힌트 없이 거의 다 썼지만, 스스로 "완벽하지 않다"고 판단했다. 지금까지 두 번의 generics 연습(PagedResult<T>, ApiResponse<T>)은 전부 type parameter 하나였다. 그런데 generics cheatsheet에 이미 적어둔 Spring Data JPA 브릿지, JpaRepository<Receipt, Long>는 type parameter가 두 개다. invoice-app에서 곧 직접 쓸 그 모양을, 오늘 손으로 직접 만들어본다.

오늘은 두 파트로 나눠서 진행한다 — ① hands-on 코드 작성(아래), ② 코드 없이 말로 설명하기(코드를 다 쓰고 나서 채팅으로 진행, 이 문서엔 질문만 적어둔다).

Part 1 — Hands-on: InMemoryRepository<T, ID>

Spring Data JPA의 JpaRepository<T, ID>는 실제로는 database를 쓰지만, 오늘은 그 인터페이스 모양만 흉내내서 Map에 저장하는 아주 단순한 버전을 만든다. 시작 코드 없이 처음부터 작성한다. 0009(collections)의 Map과 0010/0011의 generic class/method가 합쳐지는 지점이다.

1) practice/0012-review-generics-repository/p0012/Employee.java — 감쌀 대상. field: id(Long), name(String), department(String). constructor 하나(세 값 다 받음), getter 세 개. (새로 배울 것 없음 — 이미 여러 번 만든 수준.)

2) practice/0012-review-generics-repository/p0012/InMemoryRepository.java — 오늘의 핵심. 아래 조건으로 작성:

  • class 자체가 두 개의 type parameter <T, ID>를 갖는다. (JpaRepository<T, ID>와 같은 자리.)
  • field: Map<ID, T> store — constructor에서 new HashMap<>()로 초기화.
  • method 세 개 (전부 instance method, class의 T/ID를 그대로 씀 — 0011의 static method와 다르게 <T>를 method 앞에 또 선언하지 않는다):
    • T save(ID id, T entity) — store에 id 키로 entity를 넣고, 그 entity를 그대로 반환
    • T findById(ID id) — store에서 그 id로 찾은 값을 반환 (없으면 null — Map.get이 원래 그렇게 동작한다, 별도 처리 필요 없음)
    • boolean deleteById(ID id) — 그 id를 store에서 제거하고, 실제로 뭔가 있었는지(제거 전에 있었는지)를 boolean으로 반환
  • int count() — 현재 저장된 개수 반환

3) practice/0012-review-generics-repository/p0012/Runner.java — 완성본 없이 직접 작성:

  • InMemoryRepository<Employee, Long> 하나 생성
  • Employee 두 개 생성해서 각각 다른 id로 save
  • 존재하는 id로 findById → 이름 출력
  • 존재하지 않는 id(예: 999L)로 findById → null인지 출력
  • 저장했던 id 하나를 deleteById → 결과(true) 출력
  • count() 출력 (삭제 후 몇 개 남았는지)
스스로 체크리스트 (다 쓰고 나서 코드를 다시 읽으며 확인):
  • class InMemoryRepository<T, ID>처럼 콤마로 구분된 두 개의 type parameter를 class 선언에 붙였는가?
  • Map의 key 타입과 value 타입이 <ID, T> 순서로 InMemoryRepository<T, ID>의 순서와 반대인 걸 알아챘는가? (Map<K, V>는 원래 key가 먼저다 — 이번 class는 T를 먼저 선언했을 뿐, 둘은 별개의 순서다.)
  • save/findById/deleteById/count 앞에 <T>를 또 선언하지 않았는가? (0011의 static method와 다르게, 이번엔 instance method라서 class의 T를 그대로 쓸 수 있다 — static context가 아니기 때문.)
  • Runner에서 InMemoryRepository<Employee, Long>를 쓸 때, Employee와 Long 각각이 어떤 type parameter의 type argument인지 짚을 수 있는가?

Part 2 — 코드 없이 말로 설명하기

Part 1을 다 쓰고 컴파일·실행까지 확인한 다음, 코드나 이 문서를 다시 보지 않고 채팅으로 아래 질문에 답한다. 정확한 단어보다 본인 말로 원리를 짚는지가 중요하다.

  1. type parameter와 type argument의 차이를, "parameter"/"argument"라는 단어를 안 쓰고 다른 표현으로 설명해보기.
  2. InMemoryRepository<T, ID>가 왜 type parameter 하나가 아니라 두 개가 필요한지 설명해보기.
  3. findById가 T 대신 Object를 반환하도록 선언했다면 Runner에서 무슨 문제가 생기는지 설명해보기.
  4. class 선언의 <T, ID>와, 0011에서 썼던 static method 앞의 <T>가 왜 같은 글자를 써도 서로 다른 선언인지 설명해보기.
  5. 오늘 만든 InMemoryRepository<Employee, Long>가 cheatsheet의 JpaRepository<Receipt, Long>와 어떻게 대응되는지 (Employee는 뭐에 해당, Long은 뭐에 해당) 설명해보기.
Part 1에서 막히면 바로 물어보되, 먼저 0011의 ApiResponse<T> 코드와 비교해서 뭐가 같고 뭐가 다른지 스스로 짚어본 다음 물어보자. Part 2는 정답을 맞히는 게 목적이 아니라 설명이 막히는 지점을 찾는 게 목적이니, 막히면 그 지점에서 바로 질문하면 된다.
