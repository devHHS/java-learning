# 0004 — class, object, constructor 복습 (retrieval, 다른 도메인)

- **날짜**: 2026-08-11
- **레슨**: [lessons/0004-review-class-object-constructor.html](../lessons/0004-review-class-object-constructor.html)
- **관련**: 0003의 복습 세션. 큐 번호는 소비하지 않음 (큐는 이미 0003에서 3/11 체크됨)

## 배경

0003(Money 연습)을 마쳤지만 "전체적으로 애매함"이라 화요일에 다른 도메인(PageRequest, 시작 코드 없음)으로 재연습.

## 확인된 이해도

- **recall 퀴즈**: this / 0 / new 세 개는 바로 정답. fail fast 용어만 위치를 못 찾아 알려줌 (에이전트가 처음 안내한 위치가 실제로 틀렸던 것도 있었음 — 레슨 0003의 근거 위치가 부정확했던 문제, 추후 레슨 수정 시 참고).
- **hands-on (PageRequest, 시작 코드 없이 처음부터 작성)**:
  - class 구조, constructor, `this` 대입은 **첫 시도부터 정확하게** 작성함 — 0003에서 겪었던 field 초기화 누락 실수가 재발하지 않음.
  - 스스로 낸 실수 두 가지, 둘 다 **가벼운 힌트 한 번**으로 바로 수정: (1) page 0-based 조건을 `< 1`로 잘못 걸었던 것 → `< 0`으로 수정. (2) `nextPage()`를 Money의 `add(other)` 패턴을 그대로 따라 불필요한 파라미터를 받게 설계했던 것 → "인자 없이 this만으로 계산" 방향 제시 후 바로 무인자 메서드로 수정.
  - 테스트 케이스 3가지(정상/음수 page/size 초과) 모두 개별 실행으로 확인. 원본 object가 `nextPage()` 호출 후에도 안 바뀌었다는 것을 값 비교(`2`, `3`)로 직접 증명함 — 이건 에이전트가 요청해서 추가한 것이라, 자발적으로 "원본 불변 확인"까지 설계하진 않았음.

## 다음에 참고할 것

- **0003 기록의 우려("field 초기화 누락", "if 밖으로 흐름", 등)는 이번 세션에서 재발하지 않음** — 하루 간격 재현으로 storage strength 형성된 것으로 판단. 다음 복습은 간격을 더 늘려도 될 듯 (다음 주 일요일 회고 때 다시 짧게).
- 남은 약점: **"원본이 안 바뀌었는지 확인하는 테스트를 스스로 설계"**하는 습관은 아직 자발적이지 않음 — 다음에 불변(immutability) 관련 hands-on에서 이 부분을 명시적으로 요구할 것.
- 다음 큐 항목(access modifiers)로 진행 가능한 상태로 판단.
